# 常见问题与已知边界

> 返回 [README](../README.md)

## 安全须知

- 本服务需要挂载 `/var/run/docker.sock`，**等同于宿主机 root 权限**。
  请只在可信内网使用；一旦要让端口离开内网，务必在「设置」里配上访问密码，
  并不要把端口直接暴露到公网。访问密码**默认为空即不启用登录**。
- 认证用 HTTP Basic，但**静态页面本身允许匿名访问，只有 `/api/*` 需要凭据**。
  这么做是因为飞牛桌面用 iframe 加载页面：页面若被 401 挡住，浏览器会弹出原生
  登录框，在 iframe 里体验很差，个别壳还会直接判定页面不可用显示成白屏。
  页面自己渲染了登录层，凭据存在 `localStorage`，随每个请求的头部发送。
- 服务会主动拒绝更新自身容器（依据 `SELF_CONTAINER` 与容器内 hostname 双重判断）。
- 更新前会把旧容器重命名为 `<原名>-old-<时间戳>` 再创建新容器，
  因此**回滚是有现场保障的**，不是「删了重建」。
- 匿名卷（镜像里 `VOLUME` 声明但未显式挂载的卷）会被显式指回原卷名，
  避免重建后数据落到新的空卷上。

## 已知边界与取舍

这些是刻意留下的限制，不是没做完 —— 每一条都对应一个「如果放开会出事」的场景。

| 情况 | 行为 | 原因 |
| --- | --- | --- |
| 容器带 `--rm`（AutoRemove） | **直接拒绝更新** | 停止后会被 Docker 立即回收，回滚没有现场可用 |
| 容器用 `network_mode: host` | 允许更新，但会提示端口短暂不可用 | 重建期间宿主机端口确实会断开几秒 |
| 容器用 `network_mode: "container:xxx"` | 允许更新，网络由被共享的容器决定 | 这种情况下不能自己指定网络端点 |
| 容器用 `--volumes-from` / 旧式 `--link` | 允许更新，但会打警告 | 依赖的外部关系无法替你验证 |
| 目标是自己（`SELF_CONTAINER` 或容器内 hostname） | **拒绝更新** | 更新自己会导致进程被杀、任务中断在半路 |
| 同一时刻的并行更新 | 只允许一个 | 并发重建会互相争抢容器名与端口 |
| 服务端口（飞牛版） | 固定 `19999`，不提供修改入口 | 飞牛桌面入口是静态配置，改了端口入口就指向一个没人监听的地址 |
| 镜像加速地址 | **只作用于 Docker Hub** | 公共加速站基本只缓存 Docker Hub 的镜像，把 ghcr.io / quay.io 的请求改发过去只会得到一片 404 |
| 从 Docker 守护进程读加速器 | 只在「加速地址留空」时兜底生效 | 网页里显式填写的一律优先，否则用户就没办法覆盖它了 |
| 内置默认加速地址 | `docker.1ms.run,docker.xuanyuan.me`，排在「显式配置 → 守护进程」之后兜底 | 新装用户什么都不配也不该看到一整列「未知」；1ms.run 实测最快，轩源作备用 |
| `DOCKER_HOST=npipe://`（Windows 命名管道） | 不支持，启动时报错并给出替代方案 | 本服务按 Linux 部署设计，不为它引入 Windows 专用依赖 |

## 容器列表整列「未知」

查镜像摘要是服务自己发 HTTP 请求，**不经过 Docker 守护进程**，所以不继承
`daemon.json` 里的 `registry-mirrors`。「Docker 拉得动镜像」≠「检测能成功」。

排查顺序：

1. 进「设置」→ 点「检测注册表连通性」，看每个源的耗时或失败原因；
2. 全是超时 → 加速地址没生效，或者填的站不可用。换一个可用的加速站，或直接填
   `docker.1ms.run`；
3. 报 401 / 需要登录 → 那个加速站要凭据，换掉它；
4. 只有某个私有仓库失败 → 填 `REGISTRY_AUTH`，形如 `ghcr.io=user:token`；
5. 自建 http 注册表 → 只有回环地址（`localhost` / `127.0.0.0/8` / `::1`）会自动走
   http，局域网 IP 需要临时开 `REGISTRY_INSECURE`，但那样**所有**源都会改走 http，
   用完记得关。

## 消息收得到，点按钮没反应

### 飞书

两条独立链路：发消息走 `im/v1/messages`，按钮点击走长连接回调。
按顺序检查：

1. 「事件与回调」里**是不是在「回调配置」标签页**加的 `card.action.trigger`
   ——加到旁边的「事件配置」完全不生效；
2. 「应用能力 → 机器人」里的**「消息卡片」开关**是否打开；
3. 改完权限/回调后**有没有发布新版本** —— 没发布点按钮会报 `200340`，但卡片照收；
4. 设置页的「发送飞书测试卡片」→ 点那张卡上的按钮 → 看是否出现「✅ 已收到按钮回调」。
   90 秒内没反应，设置页会提示该查哪两处。

详见 [飞书配置](feishu.md)。

### Telegram

发消息走 `sendMessage`，按钮点击走长轮询回来的 `callback_query`，也是两条独立链路。
按顺序检查：

1. Token 是否带全（`数字:字母`，冒号前后都不能少、不能多空格）；
2. 群里说普通聊天 bot 读不到（成员列表写「无权读取消息」），先 `@它` 说一句，
   或 `@BotFather` → `/setprivacy` → `Disable` 后把 bot 移出群重进；
3. 这个 bot 是否在别处设过 webhook —— **webhook 与长轮询互斥**，
   打开 `https://api.telegram.org/bot<TOKEN>/getWebhookInfo` 看 `url` 是否为空，
   非空就先 `deleteWebhook`；
4. 这台机器能不能访问 `api.telegram.org`，不通就在设置页填自建的 API 反代地址；
5. 设置页「发送测试消息」→ 点消息里的按钮 → 看是否出现「✅ 已收到按钮回调」。

详见 [Telegram 配置](telegram.md)。

## 换飞书应用后报错和配置毫不相干

换凭据时**必须清掉缓存的 `tenant_access_token`**，否则会拿旧 token 发消息、
报一堆看似无关的错。本服务已处理（`ApplyFeishu` 里清缓存），
若你改的是代码而不是配置，注意别把这一步弄丢。

## 升级 fpk 后页面还是旧样式

静态资源一律带 `Cache-Control: no-cache, no-store, must-revalidate`。
内嵌资源没有 mtime，浏览器会按启发式规则猜缓存时长。如果仍然看到旧版本，
强制刷新一次（Ctrl/Cmd + Shift + R）。

## 更新到一半失败，容器起不来

回滚是默认开启的（`ROLLBACK_ON_FAILURE=true`）。失败时会：

1. 新容器创建/启动失败 → 直接删掉新容器，把 `<原名>-old-<时间戳>` 改回原名并启动；
2. 新容器起来了但健康检查没过 → 同上。

如果旧容器已经被改名却没能改回来（极少见，通常是守护进程中途异常），
手工恢复：

```bash
docker ps -a | grep '\-old-'          # 找到备份容器
docker rename <原名>-old-<时间戳> <原名>
docker start <原名>
```

设 `KEEP_OLD_CONTAINER=true` 可以让成功时也保留旧容器，方便对照排查。

## 为什么不用 Watchtower / 为什么不自动更新

可以自动 —— 把 `AUTO_UPDATE=true` 打开就是发现即更新。默认关掉是因为
容器重启会短暂断服务，很多人希望先看一眼更新说明再决定。
本项目最初的定位就是「**把决定权留在人手上，但把操作成本降到一次点击**」。

## 为什么不做成 Watchtower 那样一个容器搞定

它就是这么做的。区别在于多了「确认」这一步，以及容器与镜像分开管理、失败能回滚。
